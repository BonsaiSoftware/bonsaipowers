3Canonical workflow — skill chain

0
using-superpowers (meta)
Auto-loaded at SessionStart. Teaches the agent: "if 1% chance a skill applies, invoke it via the Skill tool before responding."
↓
1
brainstorming · IRON LAW — HARD GATE
No code, no scaffolding, no skill invocations until a design has been presented AND approved. Writes docs/superpowers/specs/YYYY-MM-DD-*.md.
↓
2
writing-plans
Bite-sized tasks, exact file paths, complete code (no placeholders), self-review for coverage. Assumes you're already in a worktree.
↓
3
using-git-worktrees · REQUIRED before execution
Invoked by brainstorming Phase 4, subagent-driven-development, and executing-plans — not by the session itself. Creates isolated workspace, verifies .gitignore, runs project setup, verifies clean test baseline. If none of the three callers fire, this step is skipped entirely.
↓
4a
subagent-driven-development
Default. Calls using-git-worktrees first, then dispatches implementers + spec-reviewers + code-quality-reviewers per task.
4b
executing-plans
Inline variant — runs in the same session. Also calls using-git-worktrees first.
Fire at every step
  • test-driven-development — no production code without a failing test first
  • verification-before-completion — no completion claims without fresh verification evidence
  • systematic-debugging — no fixes without root-cause investigation; stop after 3 failed attempts
  • requesting-code-review ↔ receiving-code-review — both directions per task
  • dispatching-parallel-agents — when ≥3 independent failure domains exist
↓
5
finishing-a-development-branch
Merge · PR · keep · discard — structured decision, not ad-hoc.

Customization hooks — the survival matrix

Everything below lives in ~/ or your repo. Nothing under the plugin dir survives /plugin update.
# What you get Where it lives Scope Use for
[C1] Custom hooks ~/.claude/settings.json global Auto-inject context, pre-flight checks, enforce repo rules at session boundaries
[C2] Project overrides <project>/CLAUDE.md repo Narrow or disable a skill for one project (e.g. "skip brainstorm for <50 LOC")
[C3] Global overrides ~/.claude/CLAUDE.md global Personal always-on rules ("never use emoji", "prefer rg over grep")
[C4] Personal skills ~/.claude/skills/<name>/SKILL.md global Reusable skills across every project you work on
[C5] Project skills <project>/.claude/skills/<name>/SKILL.md repo Skills only this codebase needs — domain-specific review, migration rules, etc.
[C6] Project MCPs <project>/.mcp.json repo Shared team tools (Linear, GitHub, internal docs) — commit to git
[C7] Personal MCPs ~/.claude.json via /config global Personal tools (Figma, personal Notion, personal GitHub account)
Three leverage points, cheapest first:
1. Gate behavior → CLAUDE.md (C2/C3). No new skills to maintain.
2. Add discipline → custom skill (C4/C5). Follow writing-skills iron law: RED→GREEN→REFACTOR per skill.
3. Expand tools → MCP (C6/C7). Orthogonal to skills; a skill can then reference mcp__server__tool by name.
